## M7 Five Implementation Sessions (Phases 60–70 Execution Unit Plan)

Phase IDs `60`–`70` are retained for traceability and acceptance checklists, but **M7 MUST be executed as five practical sessions** rather than eleven standalone commits:

| Session | Phases Covered | Files & Tasks | Expected Result | Effort |
|---|---|---|---|---|
| **Session 1 — Contract and manifest-first Rust work** | Phase 60, Phase 63 (manifest) | Inspect Phase 59 compiler results, CLI, layout types, targets and CI. Finalize the oracle ADR and versioned manifest schema. Implement manifest emission as the first Rust code change; define logical-to-physical layout direction and validate fields against compiler results. | A tested, machine-readable compile manifest with target, widths, layouts, phase, compiler identity, output identity and metrics; no guessed metadata. | **M** |
| **Session 2 — Pinned environment and real-QASM compatibility** | Phase 61, Phase 63 (QASM import) | Pin Python, `qiskit` and `qiskit-qasm3-import`. Import and simulate actual QCC-emitted physical QASM, including representative `gphase`, `sx`, `cx`, `rz` and parameter-expression forms. Document exact support and semantics-preserving fallback/unsupported behavior. | A reproducible environment and an explicit compatibility result for the real QCC output path; no silent semantic loss. | **M** |
| **Session 3 — Canonical cases, runners and comparator** | Phases 62–66 | Build neutral canonical fixtures and independent Qiskit/QCC adapters. Implement black-box execution, endian/layout normalization, common-phase semantic comparison, full physical clean-ancilla checking and the informational strict phase-accounting diagnostic. | The same logical intent reaches both systems independently; comparator handles layouts, endianness, phase and ancillas. | **XL** |
| **Session 4 — Fault injection and difficult corpus / fair baseline** | Phases 67, 68, 70 (baseline) | Test known-equivalent and deliberately corrupted circuits, including manifest phase, layouts, CX orientation and ancillas. Expand deep/non-adjacent/high-SWAP linear/ring cases (1,000+ cases). | **Session 5 — CI gate and v0.2 acceptance** | Phases 69, 70 (acceptance) | Integrate required deterministic PR checks and broader seeded main/release/scheduled runs. Preserve complete failure artifacts, publish machine-readable/README results, verify all sources and complete the acceptance report. | Independent oracle is a permanent in-repository CI regression capability; v0.2 acceptance is evidence-backed. | **L** |

**Checkpoint & Gating Policy**:
- Default starting unit after Phase 59: **M7 Session 1**.
- Create a meaningful Git checkpoint after each session's exit gate passes; stop if a contract or test exposes an unresolved correctness issue.
- Do not begin **M8** until **M7 / v0.2** passes its acceptance gate.
- Do not begin **M10** optimizer work until oracle/routing benchmark results identify a concrete gap.
- **M11** bounded hardware profiles are **optional** and require an explicit go/no-go decision after M10.
- Noise/density-matrix simulation, dynamic execution, provider adapters, KAK, and MPS remain **deferred** outside Phases 60–85.

## Phase 060 — Independent oracle architecture and acceptance contract

| Attribute | Specification |
|---|---|
| **Phase Number** | **Phase 60** |
| **Exact Phase Title** | Independent oracle architecture and acceptance contract |
| **Milestone** | Milestone M7: Independent Verification Oracle (`M7`) |
| **Relative Engineering Effort** | **M** |
| **Execution Session** | M7 Session 1 |

### 1. Objective
Define the oracle boundary and the exact correctness claims QCC will make in v0.2.

### 2. Required Concepts & Background
Independent reference models, semantic test domains, compiler black-box testing, reproducibility and acceptance criteria.

### 3. Prerequisites & Dependencies
Phase 59 integrated pipeline; existing Phase 45 layout-aware equivalence contract; current target definitions.

### 4. Ordered Implementation Tasks
1. Inspect the actual Phase 59 compiler API/CLI, emitted physical circuit format, target registry and initial/final layout result types. Record observed interfaces; do not assume command names or output schemas.
2. Define the first supported oracle domain as static unitary circuits over a declared gate subset. Reject measurement, reset, noise and dynamic control unless a separate supported behavioral comparator is explicitly added later.
3. Define two distinct Qiskit roles: (a) construct/execute the independent logical reference used for semantic verification; (b) transpile the same logical case as a separate optimization baseline.
4. Define the end-to-end comparison contract: QCC compiled physical output, actual target, initial layout, final layout, global phase and physical-qubit count are required inputs. The first Rust implementation deliverable is a stable machine-readable compile manifest exposing these values; define its schema and mapping direction here.
5. Define the test levels: exact unitary reconstruction for tractable sizes; deterministic statevector tests for broader small cases; seeded random normalized input states for larger cases. Label each mode honestly.
6. Record a short ADR describing oracle independence, supported domain, tolerances, artifact format, CI tiers and explicit exclusions.

### 5. Expected Files and Modules
```text
docs/adr/ADR-00xx-independent-oracle.md; tools/independent_oracle/README.md; docs/verification.md.
```

### 6. Required Tests
Review the contract against Phase 45/59 semantics; include examples of supported and explicitly rejected circuits; ensure the semantic reference and transpilation baseline are not conflated.

### 7. Definition of Done
The oracle contract is approved and can be implemented without adding a Qiskit dependency to Rust crates or changing compiler semantics.

### 8. Failure Modes & Debugging Considerations
Assuming Qiskit transpilation alone proves QCC correctness; comparing only output probabilities; silently accepting unsupported non-unitary programs; assuming missing layout metadata.

### 9. Explicit Exit Gate
> **EXIT GATE**: A written contract defines the independent reference, QCC outputs, comparison modes, layouts, phase, ancillas, versions, artifacts and CI acceptance gates. The manifest schema explicitly defines logical-to-physical layout direction and required fields.

## Phase 066 — Common-global-phase and full physical-state comparator

| Attribute | Specification |
|---|---|
| **Phase Number** | **Phase 66** |
| **Exact Phase Title** | Common-global-phase and full physical-state comparator |
| **Milestone** | Milestone M7: Independent Verification Oracle (`M7`) |
| **Execution Session** | M7 Session 3 |

### 1. Objective
Compare QCC compiled output with the independent logical reference using the entire routed physical state.

### 2. Required Concepts & Background
Complex inner products, phase estimation, full-statevector comparison, ancilla restoration and numerical tolerances.

### 3. Prerequisites & Dependencies
Phase 65.

### 4. Ordered Implementation Tasks
1. Simulate the QCC emitted physical circuit with the independent Qiskit execution path using the embedded physical input.
2. Compare with the independently simulated logical reference embedded through the QCC final layout.
3. Estimate exactly one common phase for the whole semantic comparison; do not estimate a new phase for each input state or basis column. This phase-invariant comparison remains the authoritative semantic pass/fail result.
4. Add a separate strict phase-accounting diagnostic: compare the canonical reference's phase-sensitive operator with the emitted physical circuit and QCC's recorded phase accounting under one fixed convention. Account for phase introduced by valid synthesis/decomposition; do not merely compare input and output `gphase` tokens.
5. Report strict phase accounting as `PASS` only when all relevant phase contributions are independently reconstructed and agree within a separately configured tolerance. Otherwise report `MISMATCH` or `UNVERIFIED`; initially this diagnostic is informational and does not override semantic equivalence.
6. For small physical widths, reconstruct/compare all computational-basis columns or full operators; separate statevector, operator and phase tolerances.
7. For larger circuits, compare a recorded set of deterministic basis and random normalized complex input states; label the result as sampled semantic testing, not exhaustive proof.
8. Enforce the clean-ancilla rule: every physical qubit outside the final layout image must return to `|0⟩`; compare full physical vectors and never trace out spare qubits.
9. Return actionable diagnostics: worst amplitude/index, semantic phase estimate, strict phase-accounting status/delta, norm difference, layout, case ID and tolerance.

### 5. Expected Files and Modules
```text
tools/independent_oracle/equivalence/{unitary,global_phase,ancilla}.py; tools/independent_oracle/schema/comparison_result.json.
```

### 6. Required Tests
H·H identity; SWAP decomposition; phase-only equivalent pair; deliberate manifest/output phase-accounting corruption; relative-phase defect; output permutation; residual ancilla population/entanglement; zero-amplitude edge cases.

### 7. Definition of Done
The independent comparator distinguishes semantics-preserving compilation from phase, layout, endianness and ancilla errors. The separate phase-accounting diagnostic reports only independently substantiated `PASS`, `MISMATCH` or `UNVERIFIED` results.

### 8. Failure Modes & Debugging Considerations
Using output probabilities only; per-input phase fitting; comparing only logical subsystem after tracing spare qubits; loose tolerances; incorrectly treating any valid synthesis phase change as a bug; claiming phase-accounting `PASS` without reconstructing all contributions.

## Phase 070 — Fair Qiskit comparison and v0.2 acceptance report

| Attribute | Specification |
|---|---|
| **Phase Number** | **Phase 70** |
| **Exact Phase Title** | Fair Qiskit comparison and v0.2 acceptance report |
| **Milestone** | Milestone M7: Independent Verification Oracle (`M7`) |
| **Relative Engineering Effort** | **L** |
| **Execution Sessions** | M7 Session 4 (fair baseline), Session 5 (acceptance report) |

### 1. Objective
Publish a transparent comparison of QCC and Qiskit on semantically verified, like-for-like workloads.

### 2. Required Concepts & Background
Transpiler configuration fairness, metric definitions, benchmarking and evidence-based reporting.

### 3. Prerequisites & Dependencies
Phases 64, 68 and 69.

### 4. Ordered Implementation Tasks
1. Define comparison conditions for each target: same logical input, native gate basis, directed coupling constraints, physical width and supported gate subset.
2. Define a primary multi-trial policy: run QCC and Qiskit with the same declared trial count $N$, record every seed/configuration and per-trial result, and report best, median and worst outcomes plus spread. Include each tool's elapsed compile time and clearly state that equal $N$ is not necessarily equal compute budget.
3. For Qiskit, document whether the selected transpiler configuration itself performs internal randomized trials; avoid accidentally comparing QCC best-of-$N$ against Qiskit best-of-$N \times M$. Record Qiskit's internal trial controls where exposed.
4. Define metric semantics before collecting results: total emitted gates, CX count, explicit final SWAP count, router-inserted SWAP-equivalent count when available, depth and compile time.
5. Do not mix logical SWAPs, router-inserted SWAPs and final emitted SWAP instructions. Document any metric that cannot be made directly comparable.
6. Generate a machine-readable result table and a README summary by circuit family, size and target; include equivalence status and configuration versions.
7. Include cases where QCC loses or produces larger/deeper circuits. Avoid global-optimality, universal superiority or unsupported speed claims.
